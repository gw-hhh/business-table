# 测试与验收规范

新增能力先写失败用例再实现，Bug 先补可复现用例；测试应验证用户可观察的行为、状态边界和失败恢复，不以函数存在或按钮可见代替功能验收。开发规则见[开发规则](02-开发规则.md)，当前实现和风险见[当前状态](../01-项目入门/03-当前状态.md)。

## 分层验证

| 层次 | 必须证明 |
| --- | --- |
| 纯函数与 Runtime | 配置校验、稳定 ID、Feature Gate、能力守卫、类型化值、查询与分页、快照隔离、并发取消及乱序保护。 |
| 组件挂载 | 默认、自定义和 Headless 入口共用状态；草稿、应用、取消、只读、错误及重试能贯通到正式表。 |
| 浏览器 | 开发服务器和生产预览中的真实交互、布局、窄屏、键盘、焦点、滚动和弹层；与旧版页面逐项对照。 |
| 文件与外部接口 | 导出文件须实际解析字段、类型、范围与格式；远端查询、权限、持久化和服务端导出须由真实适配器另行验收。 |

## 本地完整门禁

交付前运行 `npm run verify:release`，保留本次退出码和测试输出。完整门禁包含文档目录及链接审计 `audit:docs`、portability/SFC 审计、`vue-tsc`、Vitest（含挂载）、声明及库构建、独立包消费审计、Demo 构建，以及 Playwright Chromium 的开发和生产预览场景。Windows 的 `verify-release.cmd` 还执行锁文件依赖安装和 Chromium 安装；[工作流](../../.github/workflows/verify.yml)在 `development`、`main` 的推送及 PR 上执行安装和门禁。文档审计脚本见 [docs-audit.mjs](../../scripts/docs-audit.mjs)。

浏览器用例使用运行错误采集，`console.error`、`pageerror`、原生 `window.error`、`unhandledrejection` 都必须为 0。以实际运行记录为准：本地 PASS 不等于远端 CI PASS，单测通过不等于视觉接受，构建通过不等于业务后端已验收。只运行子集时，应明确说明未覆盖的层次和场景，不宣称完整 Release Gate 通过。

## 验收记录与交付

- 每批记录需求、实际修改、测试命令及结果、浏览器对照、已知限制和剩余项。旧版能力只作产品基线，不导入旧 JS 或用旧测试冒充新版覆盖。
- 用户本轮要求保留 `main` 与 `development` 分支；日常开发优先在 `development` 推进，不自动创建 feature 分支，也不自动合入 `main`。先在本地完成验证，再按用户授权推送；视觉改动仍需用户体验验收。历史文档中的固定 feature 流程以这一最新安排为准。
- 需要发布或合并时，核对目标分支及对应 CI 的真实结果。未通过完整门禁或仍缺浏览器/服务端验收的能力，按实际完成范围表述。

运行入口见[本地运行与接入](../01-项目入门/02-本地运行与接入.md)；各批证据见[验收记录索引](../06-验收记录/README.md)。
